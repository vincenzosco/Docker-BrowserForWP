# Security and the threat model

The single most important sentence in this repository: **the operator of this
server can read every page that passes through it, including passwords typed into
login forms.** That is not a flaw to be fixed. It is the architecture, and anyone
who deploys this for other people owes them that sentence.

What follows is what is actually protected, what is not, and who each protection
is against.

## What the phone is trusting

A phone connecting to this server is trusting it with:

- Every URL it visits.
- Every byte of every page, including anything rendered inside a form field.
- Every keystroke it sends, which includes passwords and card numbers typed into
  pages the server is rendering.
- Its session cookies for every site, because the cookies live in Chromium on
  this machine and never reach the phone at all.

There is no design here that avoids this. A server that can draw a page can read
it. If that trade is not acceptable, the alternative is not a better protocol --
it is not using remote rendering.

## What IS protected

### The transport

TLS 1.3 only. `minVersion` and `maxVersion` in `src/server.js` are both
`TLSv1.3`, and the cipher list is restricted to the two suites the phone's
own TLS implementation supports. A client that cannot do TLS 1.3 cannot connect,
which is the point: the phone implements TLS 1.3 in managed code, so accepting
TLS 1.2 would only create a downgrade path.

### The payload, on top of the transport

Every frame after the handshake is sealed with AES-256-GCM, under keys derived
from the device token:

```
prk    = HKDF-Extract(salt = sessionSalt, ikm = deviceToken)
keyC2S = HKDF-Expand(prk, info = "bfwp/render/v1/c2s", 32)
keyS2C = HKDF-Expand(prk, info = "bfwp/render/v1/s2c", 32)
nonce  = the frame's own sequence number, big-endian, in the last 4 bytes
aad    = the 16-byte frame header
```

This is defence in depth, and it is specifically against a **TLS terminator in
front of this process**: a reverse proxy, a load balancer, a CDN, or anything
else that ends the transport and forwards to us. Such a box sees the frames and
cannot open them. It is also against a log that captures the connection.

It is NOT against the operator of this process. The operator holds the
filesystem, and the keys are derived from a token whose digest they store. An
operator who wants to read the traffic can already read the traffic -- the pages
are in Chromium's memory.

### Device tokens

- 256 bits of entropy, generated by the server, shown once, never stored.
- Only `SHA-256(token)` is written to `devices.json`, mode `0600`, written to a
  temporary file and renamed so a crash cannot truncate the registry.
- Compared in constant time, and a digest is computed even for an unknown device
  so that the response time does not reveal which device ids exist.
- A token is never logged. `src/log.js` registers every token it sees and scrubs
  every line on the way out, with a second net that redacts any base64url-looking
  run of 43 characters or more, so a token that reached a log through a stack
  trace is still caught.
- **A token belongs to one device.** The first device id that presents it claims
  it, and the claim is written to the registry before the session opens; any other
  id is refused with code 8, and the refused attempt does not move the binding. So
  a token copied to a second phone is refused rather than silently shared, and a
  token read over a shoulder does not let its holder in while the owner is using
  it. `bfwp-device release <deviceId>` is the only way a token moves, and it is an
  operator's command: a client that could release its own binding could also
  steal one.
- The device id the client sends is therefore **not a secret and not an
  authenticator**: it is a name, which is what lets the phone generate its own.
- Revoking is one command and takes effect on the next connection:
  `bfwp-device disable <deviceId>`.

### The registration page

`src/register.js`, on `BFWP_REGISTER_PORT`, is where somebody without a shell on
the server asks for a token. It mints the same single-use digest the CLI does,
shows it once, and stores only the digest -- so it adds no credential store to
protect, and it has no accounts, no passwords and no reset flow to get wrong.

- **It listens on loopback by default.** `BFWP_REGISTER_HOST` on a non-loopback
  address is REFUSED unless `BFWP_REGISTER_SECRET` is also set, because a page
  that mints credentials must not be one mistyped variable away from the open
  internet. With a secret set, every request needs it: the page and the form.
- **An operator may open it deliberately**, with `BFWP_REGISTER_OPEN=1` and no
  secret, and `src/config.js` refuses that together with a loopback bind (a page
  nobody can reach) and together with a secret (two answers to one question). This
  is the weakest configuration the server has and it is not dressed up: whoever
  finds the page can hold a token, the challenge under the form is a speed bump,
  and the only things bounding the result are the per-address limits (one token
  per address per day, three per hour) and `BFWP_MAX_SESSIONS`.
- **The page is at the root of the address, and the plain-http listener serves
  nothing but a `301`.** `BFWP_REGISTER_HTTP_PORT` exists so that typing the bare
  address in a browser reaches the encrypted page; it never serves the form, and a
  form POSTed to it is refused with a `405` and logged, because a token posted over
  plain http would be a token on the wire. `BFWP_REGISTER_URL` must be `https://`
  unless `BFWP_ALLOW_INSECURE=1`, or the redirect would send people to another
  plain-http address.
- **In Docker the interesting case is inverted, and the compose file says so.**
  The container binds `0.0.0.0`, because a published port is forwarded to the
  container's address and never to its loopback -- a page bound to `127.0.0.1`
  inside a container is reachable from nowhere. What limits who gets there is the
  host-side publish, which ships as `127.0.0.1` for all three of the page's ports;
  `BFWP_REGISTER_BIND_IP` opens them, and an access code (or a decision to go
  without one) is what keeps that one-variable change from being an incident.
- **The per-address limits count what the LISTENER sees.** Through the host-side
  publish the container is shown the Docker bridge address rather than the caller's
  (`172.18.0.1` on this deployment), so everything arriving by tunnel or from the
  server itself shares one allowance. Requests arriving from the network carry the
  client's own address. A limit must therefore never be described as per-client
  without saying which of the two paths it was measured on -- docs/DEPLOY.md keeps
  the measurement.
- **The bot check is a signed, single-use, expiring challenge** (an arithmetic
  question whose answer is in an HMAC'd envelope), a honeypot field, a minimum
  time on the form, and a per-address limit with a day and an hour window. It stops
  a script that fills forms. It does not stop somebody solving the challenge by
  hand, and it is not claimed to: the gate that matters is the loopback default, or
  the secret.
- **The page runs no JavaScript**, is served `no-store`, and carries
  `Content-Security-Policy: default-src 'none'`. A page that hands out a
  credential is the last place to want a script running.
- A token minted here is logged the way any other is: never. The address, the
  device id and the label are logged; the token is registered with the scrubber
  before the line that could contain it.

### The audio endpoint

Audio is a presigned URL, not a credential in a query string. Each session mints
a random ticket valid only for its own session id, so a proxy access log, a
`Referer` header or a screenshot of the URL does not leak the device token that
outlives the session.

### What a client may ask the server to do

`src/session.js:sanitizeUrl` refuses everything that is not `http:` or `https:`.
`file:`, `javascript:`, `data:` and `chrome:` never reach Chromium, because a
remote viewer that can be asked to open `file:///C:/...` is a file reader for
whoever holds the phone.

## What is NOT protected

- **The content.** See the top of this file.
- **A compromised server.** The token digests are on its disk and the pages are
  in its memory. Nothing in the protocol helps.
- **Denial of service.** `BFWP_MAX_SESSIONS` bounds how many devices are
  connected at once, and each one costs a Chromium page. A single device that
  loops is bounded by the frame acknowledgement, but a fleet of them is bounded
  by the host's memory and nothing else.
- **The page's own attacks.** Chromium runs in a container, but it runs. A
  same-origin script the page runs is a script this server executes.
- **Anything on the wire before the handshake.** The device id and the token
  travel inside TLS, not inside the sealed layer, because they are what the keys
  are derived from. An attacker who can read the handshake can read the token.

## Hardening the deployment

The supplied `docker-compose.yml` already does these. If you are writing your
own, keep them:

| Measure | Why |
| --- | --- |
| `cap_drop: [ALL]` | The process needs no capabilities. |
| `no-new-privileges:true` | Nothing inside should be able to gain any. |
| `read_only: true` | A browser is the most exposed component here; it should not be able to rewrite its own code. |
| `tmpfs` for `/tmp` | Chromium needs a writable scratch space, not a durable one. |
| `shm_size: 1gb` | The default 64 MB makes Chromium die for reasons that look like bugs. |
| a non-root `USER` | The image's `pwuser`. |
| a certificate from a real CA | The phone validates the chain and the name before it connects. |
| `restart: unless-stopped` | It will fall over; it should come back. |

Beyond the compose file:

- Put the devices volume on disk that is encrypted at rest, or accept that the
  digests are readable by anyone with the disk. The digests are not the tokens,
  so this is a smaller risk than it sounds, but it is not nothing.
- Do not put a logging proxy in front of the render channel if you can avoid it,
  and if you must, know that it sees frames it cannot read rather than page
  content it can.
- Rotate by re-registering: `bfwp-device remove <old>` then
  `bfwp-device add "<label>"`. There is no in-place rotation, and the phone has
  one token field.
- Watch the registry size. Every device is a row, and a row you cannot recognise
  is a row you cannot revoke.

## Reporting

This is a `0.1.0` project. If you find something, open an issue that describes
the class of problem rather than a working exploit against a live server.
